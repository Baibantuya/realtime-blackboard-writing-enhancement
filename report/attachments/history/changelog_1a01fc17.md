## 2. 原问题

原有 PS 主循环把检测、矩阵提交、内容初始化、遮挡判断和视频调度耦合在一起。现场曾出现轻移不更新矩阵、板框移出后仍保持旧矩阵、重新找回后矩阵不生效、人物遮挡误触发找板，以及 PS 改动后卡顿和输出帧率下降。

本次新增 `ps_runtime_v2` 独立运行架构，启动时不再调用 r7/r8 的旧事件循环。复用的是已验证的底层 DMA/PYNQ/DRM 驱动、UI 和内容模型运算依赖。

## 3. 最终实现

### 视频与 PS 运算分开调度

`scheduler.py` 维护最多三对 A/B 缓冲的所有权，以及 Rectify、Restore、内容结果和 Q 的状态。几何、传感器和内容分析分别放入独立进程。几何进程只接收自己拥有的 320×180 RGB565 小图，不持有相机 CMA 租约；新样本覆盖待处理旧样本。

内容计算仍有同帧正确性依赖：A 的准备工作与 Restore 重叠，随后用对应帧 B 做细化。结果须匹配捕获、帧号、板面、历史和曝光身份。80ms 截止时间内无可用结果时 Q 执行 HOLD，继续显示已有 Canvas，并单独统计 HOLD。不能把 HOLD、跳过相机输入或重复呈现计作新内容更新。

主循环不等待几何工作进程完成。慢工作进程、失效结果和进程退出都有显式状态；不会仅因旧矩阵存在就吞掉错误。DMA 未完成时不释放其源/目的缓冲。

### 四种几何行为统一处理

`geometry.py` 分别估计相机运动、板面物理边线和局部遮挡，`policy.py` 融合证据。状态为 SEARCH、CONFIRM、TRACK、OCCLUDED、UNOBSERVABLE。

| 场景 | 行为 |
|---|---|
| 未发现板面 | 寻找板框，候选连续确认后进入跟踪 |
| 板框仍完整可见，摄像头移动 | 更新相机到固定板面坐标的矩阵 |
| 相机运动预测表明板框已被画面裁切 | 连续两次出框证据后进入寻找，不再等板面大部分消失 |
| 人物局部遮挡、背景仍静止 | 保留几何，进入遮挡处理，不因缺少完整四边就重新找板 |
| 证据不足，无法区分完全遮挡与离开 | 标记不可观测，不凭空生成可信矩阵 |

矩阵版本与板面内容 epoch 分离。普通摄像头移动只改变矩阵版本；固定输出板面坐标保持一致。新矩阵在下一次空闲 Rectify 启动时生效，已在途帧继续使用各自的矩阵，不全流水清空或重新初始化 Canvas。

### 修复矩阵发布缺陷

首版独立程序的运动预测分支改变角点却没有递增版本，驱动因此跳过 `set_geometry`；出框判断还曾要求板面可见比例低于 20%。r2 修复版本递增，并对少量出框采用连续证据。新增检测角点、已启动矩阵、已完成矩阵和 PL 角点回读记录，能够区分“算出来了”和“硬件已使用”。

### 最终跟随门槛：原图 2px

r4 按操作者要求设置为原始相机像素距离 **2.0px**，比较四个角点中最大的位移。先恢复到原图尺度，再与门槛比较，因此不是小图的 2px。当前 1/6 采样时相当于小图约 1/3px。

距离相对最后一次已发布矩阵计算，缓慢位移可以累计。只有累计位移达到门槛才同时发布新角点和新版本，避免每步微小变化永远不触发，或者同一版本携带不同角点。

### 初始化、曝光与 UI

默认遵循操作者明确给出的“启动时无人”假设，自动建立内容参考。F7 在 DMA 排空后手动重置参考与 Canvas；F6 仍保存页面。F7 保留 F6 右侧的深色背景、圆角与边框。

初始化时的 `RECTIFIED PREVIEW` 过渡页已移除，深度增强页直接使用正常输出；真正找不到板面时的找板引导仍保留，F1/F2/F3 视图不变。

PS 传感器进程持续分区测光，目标 80、容差 ±6，固定白平衡保持既有设置。曝光写入前先改变 photometry 版本；不稳定期间限制内容提交，不停止相机采集。它控制一个全局曝光/增益，不能把所有局部反光都归一化，也未实现语义人物测光排除。旧 `deployment.json` 的 `restore_photometry.scope` 是继承字段，不是当前曝光控制入口。

## 6. 匹配硬件事实

硬件由原 v22 构建产生：Vivado/Vitis HLS 2021.2，器件 `xck26-sfvc784-2LV-c`，该构建的处理目标为 100MHz。操作者曾对该频率选择提出异议，本次打包不代表对频率方案的新确认。

实际整机 route 签核：WNS +0.458ns、WHS +0.010ns；LUT 93313/117120、FF 103042/234240、CLB 14607/14640、BRAM 134/144、URAM 8/64、DSP 389/1248。CLB 利用率接近满载，后续硬件修改必须重新评估容量和非负 setup/hold，不能复用旧例外。

此次没有修改该硬件。v22 原硬件已有暗部笔画及红蓝对称判色改动，八份 v15 恢复依赖保持冻结；全部随本包保留。
