# 案例 01：用分级实测定位 KV260 视频链路帧率瓶颈

## 1. 案例信息

- 日期：2026-09-22
- AI：OpenAI Codex
- 主题：KV260 摄像头、DMA/PL、预览链路的受控帧率测量和优化
- 源记录：[`2026-09-22-003-kv260-four-level-fps-optimization.md`](../../../member_b/shared_records/2026-09-22-003-kv260-four-level-fps-optimization.md)
- 记录状态：完成了四级测量和第一轮 PS 侧优化；30 fps 解码优化仍未完成

## 2. 问题背景

原系统被观察到约 19 fps，但这个数字混合了摄像头解码、DMA/PL、内存复制和浏览器预览，不能直接说明瓶颈。任务要求使用相同分辨率和有限采样窗口，把链路拆成可比较的四级。

## 3. 对话要点

以下内容根据内部会话摘要重建，**不是逐字聊天记录**。

### 用户任务

在已经连接的 KV260 上测量并优化现有 Jupyter `trial1` 视频处理链，区分四级路径，并保留可回滚的原始文件。

### AI 贡献摘要

1. 设计四级基准：合成 DMA/PL、摄像头解码、摄像头加 DMA 但不预览、完整预览路径。
2. 发现必须使用 PYNQ 虚拟环境，并恢复 `XILINX_XRT=/usr`、`BOARD=KV260` 环境；系统 Python 不能代表板端运行环境。
3. 建议复用 UVC 输入缓冲、减少每帧 DMA 输出复制，并对 JPEG/浏览器预览降采样。
4. 将结果解释为“DMA/PL 不是当前主要瓶颈，MJPEG 解码和预览尾延迟更可疑”，而不是把所有耗时归因于 FPGA。

## 4. 团队决定与采用

- 采用复用输入缓冲、减少输出复制和降低预览频率的 provisional PYNQ 基线。
- 保留原始 notebook 和部署文件；优化结果不被写成 30 fps 已达成。
- 后续优先检查 FFmpeg 解码线程、低分辨率采集或硬件加速路径。

## 5. 量化验证

| 级别 | 路径 | 结果 | 说明 |
|---|---|---:|---|
| L1 | 合成 DMA + PL，无复制 | 65.441 fps | 用户在补充 notebook 中完成的板端测量。 |
| L2 | 摄像头解码 | 24.769 fps | 120 帧，4.8448 s；中位 33.716 ms，p95 34.287 ms。 |
| L3 | 摄像头 + DMA/PL，无预览 | 25.150 fps | 120 帧，4.7715 s；说明 DMA/PL 没有造成主要额外帧时延。 |
| L4 | 摄像头 + DMA/PL + 预览 | 23.267 fps | 120 帧，5.1575 s；JPEG 预览中位耗时 46.513 ms，p95 79.896 ms。 |

另有独立 FFmpeg 解码预估 27.35 fps，但四级 notebook 的 24.769 fps 才是受控比较结果；两者不能混为同一测量。

## 6. 失败与纠正

- 第一次直接上传被板端权限拒绝，没有覆盖原文件。
- 第一次用 `/usr/bin/python3` 测试，发现缺少 PYNQ 且 OpenCV/NumPy 环境不兼容；随后改用 Jupyter 使用的 PYNQ 虚拟环境。
- 初版 notebook 没有完整暴露 L1/L4，补充了独立 notebook，并检查 JSON 可解析。
- 早期约 19 fps 与本次测量的预览频率、复制行为不同，不能作为严格 before/after 对照。

## 7. 结果边界

- 这是板端四级测量和 PS 侧优化证据，不是完整系统 30 fps 验收。
- 没有证明某一个 FFmpeg 解码线程配置一定能达到 30 fps。
- 浏览器预览产生的长尾延迟已测到，但没有完成独立显示线程或最新帧队列的实现。
