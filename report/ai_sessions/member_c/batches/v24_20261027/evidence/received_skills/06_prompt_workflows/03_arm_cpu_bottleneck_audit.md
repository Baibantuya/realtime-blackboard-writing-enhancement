# 提示词工作流 03: PS 嵌入式瓶颈 -> ARM/NEON 优化工作流

## 1. 适用场景
- 队伍的 PL 加速核运行极快，但系统整机吞吐（FPS）依然很低；
- 在 ARM Cortex-A53 / A72 等低功耗嵌入式 CPU 上运行 Python / NumPy 代码时，出现异常的高 CPU 占用率与耗时剧增。

## 2. 提示词模板 (Prompt Template)

```markdown
你是一位精通 ARM Cortex-A 架构指令集、NEON SIMD 并行加速以及嵌入式 Python 高性能优化的专家。
我的 PYNQ 系统在板端运行测试时，发现 PS 端单帧处理耗时异常严重，直接击穿了实时性预算。

【运行环境与硬件约束】：
- 处理器架构：<如 ARMv8-A Cortex-A53 4核 @ 1.33GHz，32KB L1 Data Cache，512KB L2 Cache>
- 实时性预算：<如目标 30 FPS，单帧允许给 PS 端的处理时间只有 8.0ms>
- 当前实测耗时：<如实测单帧耗时高达 65ms>

【PS 端瓶颈 Python 代码片段】：
<粘贴每帧执行的 Python / NumPy 处理代码，包括数组操作、连通域、差分或状态机>

【各步骤分段耗时探测结果】：
<粘贴逐行或逐函数耗时，例如：step_diff: 23ms, step_recover: 50ms>

请根据 ARM Cortex-A 嵌入式 CPU 的硬件物理特性（小容量 Cache、弱分支预测、较慢的单核主频、高昂的内存分配开销），为我进行深度瓶颈审计并给出优化方案：

1. **底层瓶颈深度诊断**：
   - 指出代码中是否存在频繁的大数组分配（引发底层频繁 `malloc/free` 与 CPU 内存带宽饱和）；
   - 分析是否存在跨通道广播或多重切片（如 `np.all(diff <= 4, axis=-1)`），解释为什么这种写法在 PC x86 上极快但在 ARM A53 上极慢（缺少连续 NEON 矢量化，产生大量中间临时对象并冲刷 L1/L2 Cache）。
2. **轻量化短路与工程化改造**：
   - 如何引入状态短路（Fast Short-Circuiting）：在无特定事件或状态未改变时，实现 0.01ms 瞬时跳过；
   - 是否可以先下采样（如降采样到 1/4 或 1/16 尺寸）进行全局快速粗筛，仅在有必要时对局部 ROI 进行精细计算。
3. **C++ / NEON / OpenCV 底层替换代码**：
   - 给出重构后的极速 Python / OpenCV C++ 等价实现，确保：
     a) 彻底复用预分配数组，零动态内存分配；
     b) 充分调用 OpenCV 底层由 ARM NEON 汇编优化的算子（如 `cv2.absdiff`, `cv2.inRange`）；
     c) 预期耗时需压缩到 < 5ms 以内，并给出验证正确性的单元测试。
```

## 3. 典型应用范例与产出效果
- **在白板项目中的实际应用**：在排查“写不上去也擦不掉”死锁（*Session 2026-10-24-007 / D-160*）时，利用本工作流准确定位到 `_recover_erased_material` 耗时 50.3ms 以及 NumPy 3D 跨通道规约耗时 23.5ms。依照该模板指导，删除冗余全图归约，改用 OpenCV 底层 NEON 优化的差分和裸板中性判定，单帧耗时从 **73.8ms 骤降至 1.8ms**（提速 41 倍），彻底释放了 ARM Cortex-A53 的算力瓶颈。
