## Recommended Implementation Sequence (not implemented)
1. Preserve matched firmware. Add stage counters/timers; use O_NONBLOCK and a bounded descriptor-only drain. Hold newest candidate dequeued, QBUF discarded old candidates without touching pixel payload, then copy only selected final frame for existing API. Keep copy fallback for current CPU rotate. Do not delete .copy while immediately QBUF-ing its backing buffer.
2. Preferred robust sharing: current V4L2 MMAP pool -> VIDIOC_EXPBUF plane0 -> dma-buf fd -> small PL-side kernel importer/bridge. Attach/map fd for actual rectifier DMA master, validate full-frame contiguous DMA span, mapped aperture, length/offset/alignment/stride, retain mapping and buffer reference while IP reads. Bridge should own mapping/lifetime and ideally submission/completion; fd is not an address and V4L2 mmap offset is not physical address. Without IOMMU, contiguous low-CMA backing supplies direct DDR addressing; with IOMMU DMA addresses must be mapped in the actual master's domain.
3. Alternative application-owned pool: allocate3-4 buffers from verified low-DDR CMA dma-buf exporter/heap, V4L2_MEMORY_DMABUF REQBUFS/QBUF planes[0].m.fd, same PL importer consumes them. CMA heap existence/name and below2GiB placement depend on board kernel/DT; system heap is not a physical-contiguity guarantee. Existing PYNQ allocate buffer physical_address does not itself provide a V4L2-importable dma-buf fd.
4. Quick prototype alternative USERPTR: try actual driver's V4L2_MEMORY_USERPTR with PYNQ CMA virtual addresses and sizeimage; only after verifying PYNQ/XRT mmap backing is accepted by vb2_dma_contig and synchronization/addressing. USERPTR field is CPU virtual pointer, not physical_address. Do not promise compatibility; PFN-style mappings/pinning can fail.
5. Buffer lifecycle FREE -> camera queued/writing -> DQBUF complete -> held/PL reading -> rectify completion -> QBUF. Capture3-4 buffers; drop stale complete frames without payload copies, retain newest when PL busy; ensure continuous source/backpressure/drop policy with real camera driver. Only rectifier completion is needed to release raw capture input, because restore reads separate corrected output. Do not wait restore unnecessarily. On timeout retain buffer until DMA genuinely stops/resets; don't free/requeue an in-flight read.
6. Zero-copy CPU-free input additionally needs rotation moved into rectifier addressing or validated sensor hflip/vflip. Dense RGB888 requires bytesperline5760 and compatible data_offset/alignment; padding must be handled in hardware or rejected. Existing PL register src0x10/0x14 can be changed per completed capture buffer rather than always self.src. Device-written input does not need a blind CPU flush; dirty CPU aliases could overwrite new DMA data. Driver/bridge must handle DMA synchronization; CPU access requires DMA_BUF_IOCTL_SYNC brackets; sync ioctl does not replace completion/ownership.
