# 操作流程

1. **固定资料身份。** 记录来源、接收日、版本和原始包指纹；在新目录准备必要副本。确定任务是离线核对、现场环境收集或硬件操作，不能由“预检”二字推断允许加载。
2. **选择契约。** 使用经审阅的profile。新版差异先报告，不覆盖旧profile。核对期望来自独立接口设计还是旧版观察快照；V22示例属于后者，工具不能认证其设计正确性。
3. **离线检查。** 运行独立脚本，不import发布包中的loader/runner，不调用 `Overlay`、MMIO、allocate或板卡命令。查看退出码、FAIL字段和全部not_checked。
4. **解释差异。** 缺文件追查完整发布包；哈希不符追查版本和来源；HWH不符区分格式差异、IP重命名与ABI变更；环境不符等待对应环境记录。不自动重命名硬件文件凑对、不更改预期哈希让检查通过。
5. **审核加载后端。** 仅文档层选择平台支持的加载流程和前置条件。KV260示例有bit.bin/DTBO、firmware别名、fpgautil后元数据登记；其他平台可采用其支持的Overlay流程，但需检查实际安装版本和副作用。本工具没有插件加载机制，不执行profile.backend。
6. **板测另列。** 收到用户设备与操作安排后，才按该平台流程验证环境、已加载身份、受控加载、缓冲/传输、显示、正常停止及异常占有。文件哈希不代替功能验收。
7. **保存结论。** 新报告绑定脚本、profile、输入身份和验证平台，分别写通过/失败/未检查。保留失败记录和证据层次；新版本只升级有新证据的条目。

对V22，先解决 [预检入口冲突](../../board_reproduction/entrypoint_conflict.md) 再考虑冷启动验收。不要把运行目录中的历史PID或S05先前整包核验结果当作本次运行结果。
